Lesson 1 · 10 minutes

From a Vial layout to a working ZMK fork

The central idea is a pipeline: describe hardware, describe behavior, compile two images, flash them, then version the source.

1. The mental model

Hardware description

Board DTS files say which nRF52840 pins are rows, columns, encoders, LEDs, and battery inputs.

User configuration

config/cornix.keymap maps positions to keys; cornix.conf enables features such as NKRO.

Build targets

build.yaml asks for a left central image and a right peripheral image.

Firmware

The compiler turns each target into a UF2 file for the nRF52840 bootloader.

That is why changing a source file does nothing to the keyboard until the correct UF2 is built and flashed to the correct half.

2. How we converted your original layout

Untitled.vil is Vial's saved data, not a ZMK firmware image. We read its layers and physical positions, then translated keycodes and behaviors:

  • Vial KC_Q becomes ZMK &kp Q.
  • Vial Bluetooth profile actions became ZMK &bt BT_SEL 0, 1, and 2.
  • Vial mouse middle-click became &mkp MCLK.
  • Vial NKRO magic keys became no-ops because NKRO is enabled permanently in cornix.conf.

The important debugging move was checking the physical matrix transform before reversing keys. The right row is visually reversed by the board's matrix numbering, while the left row is not; the board metadata confirmed that orientation.

3. Why the left and right images differ

The left half is the central: it owns the shared keymap state, talks to the Mac over USB or Bluetooth, and exposes ZMK Studio. The right half is the peripheral: it scans its own keys and sends positions to the left over split BLE. So a right half not appearing in ZMK Studio is normally expected.

Rule of thumb: if the left works by itself but right keys do not arrive, investigate the split BLE pairing, right-side firmware, power, and physical radio—not the Mac's NKRO setting first.

4. Why a normal reflash did not fix pairing

ZMK stores Bluetooth bonds and ZMK Studio changes in persistent flash. Installing a normal UF2 usually preserves those settings. The recovery image enables CONFIG_ZMK_SETTINGS_RESET_ON_START and disables BLE temporarily, so both halves can be cleared before either tries to pair.

1. right_settings_reset.uf2 → right half
2. left_settings_reset.uf2  → left half
3. right.uf2                → right half
4. left.uf2                 → left half
5. power-cycle both, forget the old Mac pairing, pair again

This is why adding the missing right reset image fixed your connection.

5. What “push to a fork” means

A fork is a separate GitHub repository connected to the original upstream repository. In this checkout, origin still names camh/cornix-zmk-config; fork names your personal copy. We pushed the five local commits to your fork's main branch:

git status                 # is the tracked worktree clean?
git log --oneline -5       # what commits are we publishing?
git remote -v              # where will fetch and push go?
git push fork main         # publish to your fork

The dependency folders were intentionally left untracked. They are local build inputs, not part of the configuration changes we meant to publish.

6. Your first practice change

  1. Open config/cornix.keymap and find a single &kp binding in the base layer.
  2. Change one key to another simple keycode.
  3. Run git diff -- config/cornix.keymap and explain the change in plain language.
  4. After we review it, build, flash, commit, and push it.

Quick check

Why does the right half not normally show in ZMK Studio?

Because the left half is the central and the right half is its split-BLE peripheral. Studio talks to the central.

Why reset both halves?

Each controller stores its own pairing state. Clearing only one can leave the two sides with incompatible stored bonds.

Where should a normal keymap edit go?

config/cornix.keymap, followed by a rebuild and flashing the corresponding normal firmware.
